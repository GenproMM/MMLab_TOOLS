# RELEASE_MAP — синхронизация Карты релизов с GSD

Инструментарий реализует поток, описанный в **Регламенте на выпуск и поддержку
плагинов**, п. **8.2.1** (Загрузка и планирование заданий через GSD) и **11.3**
(Взаимодействие с GSD).

## Состав

| Файл | Назначение | В git |
| ----- | ----- | ----- |
| `Сводный Реестр Плагинов - Скрипты_Карта релизов.csv` | Вход: экспорт листа «Скрипты_Карта релизов» из Google-таблицы (кладётся сюда командой `fetch` из «Загрузок») | да |
| `gsd_release_sync.py` | Инструмент синхронизации (stdlib, Python 3) | да |
| `output/` | Копия артефактов для выгрузки обратно на сетевой диск | нет (`.gitignore`) |
| `status-journal.csv` | Журнал переходов статусов заданий | нет (`.gitignore`) |

Генерируемые плановые документы (источник истины — CSV) пишутся в `.planning/`:
`release-map.json`, `ROADMAP.md`, `REQUIREMENTS.md`, `PROJECT.md`.

## Откуда берётся CSV (`fetch`)

Лист выгружается из Google-таблицы браузером — файл попадает в «Загрузки»
(`%USERPROFILE%\Downloads`; вне Windows — `~/Downloads`). Команда `fetch`
копирует его оттуда в `RELEASE_MAP/`, дальше вся работа идёт с копией в
репозитории (её же правит `status`). Перекладывать файл руками не нужно.

- берутся файлы с именем `Сводный Реестр Плагинов - Скрипты_Карта релизов.csv`,
  включая браузерные дубли `… (1).csv`; из них — самый свежий по времени изменения;
- оригинал в «Загрузках» не удаляется и не изменяется;
- содержимое совпадает с текущим CSV — копирования не происходит;
- в «Загрузках» пусто, но CSV в репозитории есть — предупреждение, синк идёт по нему;
- нет ни выгрузки, ни CSV — выход с кодом `1`;
- каталог «Загрузок» переопределяется переменной окружения `MMLAB_DOWNLOADS_DIR`
  (нестандартный профиль Windows, тесты).

## Формат CSV «Скрипты_Карта релизов»

Колонки: `Версия релиза, План релиза, Название плагина, ID, MVP, Вес, Статус,
Группа задач, Описание, Автор, Комментарий`.

Лист двухуровневый:

- **строка-заголовок релиза** — заполнена только `Версия релиза` (формат
  `vYYMMDD`), остальные колонки пустые;
- **строки-задания** — идут ниже заголовка с пустой `Версия релиза`; релиз
  наследуется от ближайшего заголовка выше.

Смысл колонок задания:

- **План релиза** — **рудимент листа: не импортируется.** Дата фазы берётся
  только из версии релиза.
- **ID** — уникальный идентификатор задания (Product ID, п. 10.2).
- **Название плагина** — плагин/кнопка, к которой относится задание.
- **MVP** — `TRUE` / `FALSE`; `TRUE` → приоритет `MVP`, иначе `Обычный`.
- **Вес** — трудоёмкость (справочно, в план переносится как есть).
- **Статус** — `Не начато → В работе → Готово → Релиз`, плюс рабочее
  «Без статуса» для незапланированных строк.
- **Группа задач** — `ФУНКЦИОНАЛ` / `ОШИБКИ` и т. п.
- **Описание** — текст задания; **Комментарий** — уточнение/примечание.

Разделитель определяется автоматически (`,` или `;`), кодировка — UTF-8.

## Соответствие «Карта релизов» ↔ GSD

| Карта релизов | GSD | Пример |
| ----- | ----- | ----- |
| Версия релиза `vYYMMDD` | фаза | `Phase v260814` |
| ID задания | требование | `REQ-2830001` |
| Версия релиза → дата фазы | дата | `v260814` → `2026-08-14` |
| Статус `Релиз` | закрытие требования | `- [x] **REQ-2830001**` |

Дата фазы выводится **только** из версии релиза; колонка «План релиза» —
рудимент листа и не импортируется. Версия с несуществующей датой (например
`v250632`) — ошибка `check`.

Закрытие подтверждает **только** статус `Релиз`: `Готово` означает «работа
сделана», но требование остаётся открытым (`[ ]`). Статус фазы выводится из
статусов её требований:

| Статус фазы | Когда |
| ----- | ----- |
| `Не начата` | все требования `Не начато` |
| `В работе` | есть `В работе`, либо часть требований ещё не сделана |
| `Готова к релизу` | все требования `Готово` или `Релиз`, но закрыты не все |
| `Закрыта релизом` | **все** требования в статусе `Релиз` |

Переходы печатаются в отчёте `sync-docs` блоком `ЗАКРЫТО:` — какое требование
закрыл новый CSV и какая фаза от этого закрылась.

## Правила синхронизации

- задание со статусом **«Без статуса»** (или пустым) **не синхронизируется**;
- задание с пустым **«Название плагина»** **не синхронизируется**;
- **MVP = TRUE** → приоритет `MVP`, иначе `Обычный`;
- **новое задание заводится только со статусом `Не начато`** (см. ниже);
- параметры уже заведённых заданий каждый синк берутся из текущего CSV.

Пропущенные задания остаются в CSV, попадают в отчёт команды и в секцию
«Не синхронизировано» в `ROADMAP.md` — это сигнал дозаполнить строку в
Google-таблице, а не потеря данных.

## Команды (Регламент 8.2.1)

```bash
# Шаг 0 — забрать свежий экспорт листа из «Загрузок» (%USERPROFILE%\Downloads)
python3 RELEASE_MAP/gsd_release_sync.py fetch

# Смена набора заданий — очистить .planning от прошлой Карты релизов
python3 RELEASE_MAP/gsd_release_sync.py reset

# Шаг 1 — валидация и генерация артефактов
python3 RELEASE_MAP/gsd_release_sync.py check
python3 RELEASE_MAP/gsd_release_sync.py sync-docs
# Упрощённо («Синхронизируй gsd» = fetch + check + sync-docs):
python3 RELEASE_MAP/gsd_release_sync.py sync

# Шаг 2-3 — ведение статусов задания
python3 RELEASE_MAP/gsd_release_sync.py status 2102010 "В работе"
python3 RELEASE_MAP/gsd_release_sync.py status 2102010 "Готово"

# Шаг 4 — выпуск
python3 RELEASE_MAP/gsd_release_sync.py status 2102010 "Релиз"
# затем скопировать RELEASE_MAP/output/ обратно в Google-таблицу / на сетевой диск
```

После `sync-docs` для планирования и исполнения фазы используются команды GSD:
`/gsd-plan-phase <N>`, `/gsd-execute-phase <N>`, `/gsd-verify-work <N>`, `/gsd-ship`.

## Смена набора заданий (`reset`)

`reset` очищает генерируемые блоки `.planning/ROADMAP.md`, `REQUIREMENTS.md`,
`PROJECT.md` и обнуляет baseline `.planning/release-map.json` — под загрузку
принципиально нового набора заданий.

Не трогает: ручной текст вне маркеров (фазы GSD `## Phase N: ...`), `STATE.md`,
`phases/`, `codebase/`, `quick/`. Пространства имён не пересекаются по
построению — `Phase vYYMMDD` / `REQ-<ID>` у Карты релизов против `Phase N: ...`
и собственных кодов требований у GSD, — поэтому новый набор не конфликтует
с текущими фазами и закрывать milestone ради него не нужно.

Baseline **обнуляется, а не удаляется**: пустая база = «в GSD нет требований»,
поэтому гейт «новое требование только со статусом `Не начато`» действует уже на
первом синке нового набора.

## Ручной текст в `.planning/*.md`

Генерируемая часть каждого документа обёрнута маркерами:

```markdown
<!-- RELEASE-MAP:BEGIN — сгенерировано gsd_release_sync.py, не редактировать -->
...
<!-- RELEASE-MAP:END -->
```

Всё **вне** маркеров регенерацию переживает — так в `ROADMAP.md` рядом с фазами
Карты релизов (`## Phase vYYMMDD`) живут ручные фазы GSD (`## Phase N: ...`);
генератор различает их по формату версии. При первой миграции файла без маркеров
скрипт кладёт резервную копию в `.planning/_legacy/` (каталог в `.gitignore`).

## Обновление заданий: CSV — единственный источник

`sync-docs` перестраивает плановые документы из текущего CSV целиком. Для уже
заведённых заданий заново берутся **все** параметры: статус (включая откат назад
по циклу), «Название плагина», «Описание», «Комментарий», «Автор», «Вес»,
«Группа задач», «MVP», «План релиза». Прошлый `release-map.json` значения не
переопределяет и обратно в CSV ничего не дописывает; задание, удалённое из
листа, исчезает из плановых документов.

Прошлый `release-map.json` используется только для двух вещей: отличить новое
задание от уже заведённого (см. ниже) и напечатать блок `ОБНОВЛЕНО:` — что
именно приехало из свежего CSV.

Следствие: правки в `.planning/*` руками бессмысленны — следующий синк их
перезапишет. Параметры заданий меняются в Google-таблице.

## Новое задание — только «Не начато»

Задание, которого не было в прошлом `release-map.json`, попадает в GSD **только**
со статусом `Не начато`. Пришедшее из листа сразу `В работе` / `Готово` / `Релиз`
— это работа, сделанная мимо GSD: она уходит в пропуски с причиной
«новое задание не в статусе «Не начато»» и в план не заводится. Чтобы завести
такое задание, выставьте в Google-таблице статус `Не начато`.

Гейт не применяется на самом первом синке (`.planning/release-map.json` ещё нет):
там заводится весь состав листа. На уже заведённые задания гейт не действует —
они спокойно идут дальше по циклу `Не начато → В работе → Готово → Релиз`.

## Команда агента

`/mm-releasemap-download` — процедура «скачать Карту релизов» (`fetch` + `check` +
`sync-docs` + разбор пропусков), канонический файл
`agents/commands/mm-releasemap-download.md`. Естественно-языковые триггеры:
«Синхронизируй gsd», «скачай карту релизов».
