# Регламент на выпуск и поддержку плагинов MM LAB

Документ описывает порядок разработки, выпуска и поддержки плагинов вкладки
**MM Lab** для Autodesk Revit (на базе pyRevit). Регламент обязателен для всех,
кто вносит изменения в `MM LAB.extension`, и согласован с базой знаний проекта
(`.planning/codebase/*`, `MMLabs_OBSIDIAN/`).

---

## 1. Назначение и область применения

- **Цель**: обеспечить единообразие, надёжность и воспроизводимость при выпуске
  и поддержке кнопок (pushbutton) вкладки MM Lab.
- **Область**: всё содержимое `MM LAB.extension/`, манифест `extension.json`,
  вендоринг зависимостей в `lib/`, а также сопутствующие процессы (GSD, сессии).
- **Аудитория**: разработчики BIM-инструментов в русскоязычном контуре,
  сопровождающие проект.

---

## 2. Архитектура плагинов вкладки MM Lab

Проект построен как **pyRevit extension** — дерево каталогов, которое pyRevit
сканирует и превращает в ленту (ribbon) Revit. Бизнес-логика живёт в
`script.py`, UI описывается декларативно в `bundle.yaml`.

> **Важно про имена.** Внутреннее имя расширения в `extension.json` — `MM LAB`,
> каталог вкладки — `MM Lab.tab`, но **отображаемый заголовок вкладки на ленте —
> `GENPRO LAB`** (`MM Lab.tab/bundle.yaml` → `title.ru`). На текущий момент
> расширение содержит **3 панели** (`АРХИТЕКТУРА`, `ИОС`, `КООРДИНАЦИЯ`) и
> **18 команд**. Используется **только тип `pushbutton`**; составные элементы
> (`pulldown`, `stack`, `splitbutton`, `smartbutton`) пока не применяются.

### 2.1. Иерархия каталогов

```
MM LAB.extension/            ← корень расширения (рядом extension.json)
└── MM Lab.tab/              ← вкладка ленты Revit
    ├── АРХИТЕКТУРА.panel/   ← панель (группа кнопок)
    │   ├── bundle.yaml      ← порядок и заголовок панели (layout)
    │   └── Высота этажа.pushbutton/
    │       ├── script.py    ← код команды (точка входа)
    │       ├── bundle.yaml  ← заголовок/тултип кнопки (en_us + ru)
    │       ├── icon.png     ← иконка кнопки
    │       └── README.md    ← опциональное описание команды
    ├── ИОС.panel/
    └── КООРДИНАЦИЯ.panel/
```

Порядок вкладок/панелей и кнопок задаётся ключом `layout` в `bundle.yaml`
родительского уровня. В `MM Lab.tab/bundle.yaml` для визуального разделителя
панелей используется элемент `-----`. Если кнопка не указана в `layout` панели,
pyRevit добавит её после перечисленных — но для предсказуемого порядка все
команды должны быть прописаны в `layout` явно.

### 2.2. Слои (соответствуют `.planning/codebase/ARCHITECTURE.md`)

| Слой | Расположение | Назначение |
|------|--------------|------------|
| Метаданные расширения | `extension.json`, `MM Lab.tab/bundle.yaml` | Идентичность расширения, порядок вкладок/панелей |
| UI-метаданные команды | `*.pushbutton/bundle.yaml` | Заголовки, тултипы, локализация (`en_us`, `ru`) |
| Исполнение команды | `*.pushbutton/script.py` | Revit API, коллекторы, транзакции, диалоги |
| Вендорные зависимости | `lib/openpyxl/**`, `lib/et_xmlfile/**` | Python-пакеты, недоступные в среде хоста |
| Планирование/автоматизация | `.github/get-shit-done/bin/*.cjs` | GSD-инструменты управления `.planning/` |

### 2.3. Поток выполнения команды

1. pyRevit читает `extension.json` и `bundle.yaml` вкладки/панелей.
2. Пользователь нажимает кнопку, разрешённую из `*.pushbutton/bundle.yaml`.
3. Runtime запускает соответствующий `script.py` и инжектит контекст `__revit__`.
4. Скрипт читает модель через `FilteredElementCollector`, считает изменения и
   пишет их через `Transaction`.
5. Скрипт сообщает результат через `TaskDialog` / `pyrevit.forms` / output-канал.

> Состояние Revit транзитивно и привязано к документу
> (`doc = __revit__.ActiveUIDocument.Document`). Отдельная БД не используется —
> данные хранятся в модели Revit.

## 3. Правила разработки

Базируются на `.planning/codebase/CONVENTIONS.md` и фактическом коде.

### 3.1. Именование и структура

- Точка входа команды всегда называется `script.py` внутри каталога
  `<Имя>.pushbutton/`.
- Метаданные кнопки — в colocated `bundle.yaml`; заголовок задаётся для `en_us`
  и `ru`.
- Функции и переменные — `snake_case` (`feet_to_meters`, `get_floor_thickness`).
- Константы — `UPPER_SNAKE_CASE` (`TARGET_PARAMETER_NAME`).
- Классы — `PascalCase` (`SystemClassificationSelectionForm`).
- Первая строка каждого `script.py`: `# -*- coding: utf-8 -*-` (кириллица в коде).
- Обязательные дандер-метаданные модуля: `__title__`, `__author__`, `__doc__`.

### 3.2. Порядок импортов

1. Стандартная библиотека (`sys`, `os`, `re`, `datetime`).
2. Загрузка CLR/Revit (`import clr`, `clr.AddReference(...)`).
3. Revit API (`from Autodesk.Revit.DB import ...`, `... UI import ...`).
4. pyRevit/UI-фреймворк (`from pyrevit import script`, `System.Windows.Forms`).

### 3.3. «Тонкие» кнопки

- Кнопки должны быть тонкими: общую/повторно используемую логику выносить из
  `script.py` в модули, а не копировать между кнопками (актуальный риск —
  дублирование helper-блоков в ИОС-скриптах).
- Вендорные зависимости подключаются через инъекцию пути:
  `sys.path.insert(0, VENDOR_DIR)` для загрузки `lib/`.

### 3.4. Обработка ошибок (запрет silent-fail)

- **Запрещены** «тихие» `except`, проглатывающие критические ошибки — это
  зафиксированный риск качества проекта.
- Guard-проверки перед записью: активный документ, наличие элементов и
  параметров; ранний выход с `TaskDialog.Show(...)`.
- Запись в модель — только в транзакции: `Transaction.Start()` →
  изменения → `Commit()` в `try`, `RollBack()` в `except`.
- Верхнеуровневая ловушка показывает ошибку в UI (`show_error(...)`), а не
  «голый» traceback.

### 3.5. Логирование

- Основной канал — `Autodesk.Revit.UI.TaskDialog` (итог/ошибка).
- Дополнительный текстовый вывод — `pyrevit.script.get_output()`.
- `print(...)` допустим только для локальных служебных заметок об исключениях.
- В операциях массовой записи/удаления **выводить счётчики** (обработано,
  пропущено, ошибок) в output-канал; при критических ошибках мутации —
  заваливать транзакцию, а не «дотягивать» с частичным результатом.
- Централизованной телеметрии в проекте нет (зафиксированный долг) — до её
  появления output-канал является минимальным обязательным следом операции.

### 3.6. Артефакты, не подлежащие коммиту

- Служебные каталоги IDE: `.vs/` (VSWorkspaceState.json, `*.sqlite`, `*.vsidx`).
- Временные/сгенерированные отчёты (например, `wet_zones_report.csv`), если они
  не являются эталонными фикстурами.
- Кэш Python `__pycache__/`, `*.pyc` для первичного кода (вендор в `lib/` —
  исключение по факту поставки пакета).

### 3.7. Деструктивные операции

Команды с массовым удалением/перезаписью (например, `Замена CAD-геометрии`
с `doc.Delete(...)`) обязаны:

- Показывать **preflight-сводку** (что и сколько будет изменено/удалено) и
  требовать явного подтверждения пользователя.
- Поддерживать **dry-run** там, где это применимо.
- **Прерывать** выполнение при критической ошибке удаления, а не продолжать с
  проглоченным исключением (см. известный баг частичной очистки).
- Выполнять всё в транзакции с гарантированным `RollBack()` при сбое.

### 3.8. Производительность

- Сужать коллекторы фильтром по категории/классу **до** итерации, не сканировать
  всю модель повторно на каждом шаге.
- Кэшировать промежуточные наборы вместо повторного `FilteredElementCollector(...)`.
- Избегать квадратичных проверок (попарный перебор bbox) на больших моделях —
  использовать пространственную сегментацию (grid/bucket).
- Для тяжёлых команд предусматривать ограничение области (активный вид/выбор/
  раздел) и индикатор прогресса.

## 4. Версионирование, выпуск и установка

### 4.1. Ветвление и коммиты

- Разработка ведётся в отдельных feature-ветках; прямой push в основную ветку
  без согласования запрещён.
- Сообщения коммитов — содержательные, на русском, в духе истории проекта
  («Добавлена панель КООРДИНАЦИЯ и кнопка Версия шаблона»).
- Один коммит = одно логически завершённое изменение.

### 4.2. Выпуск новой кнопки/панели

1. Создать каталог `<Имя>.pushbutton/` (или `<Имя>.panel/`).
2. Добавить `script.py`, `bundle.yaml`, `icon.png` (и при необходимости `README.md`).
3. Прописать порядок в `bundle.yaml` родительской панели (`layout`).
4. Проверить локализацию заголовка/тултипа (`en_us` + `ru`).
5. Прогнать ручную проверку в Revit (см. раздел 7).
6. Закоммитить и запушить в feature-ветку.

### 4.3. Установка/деплой

- Деплой выполняется установкой pyRevit extension в локальную среду
  пользователя (нет CI-публикации, нет отдельной БД).
- Версия Revit/pyRevit фиксируется в `__doc__`/`README.md` команды, если есть
  ограничения совместимости.

### 4.4. Управление вендорными зависимостями

- Пакеты в `lib/` (`openpyxl`, `et_xmlfile`) поставляются вместе с расширением и
  подключаются через `sys.path` (см. `Экспорт ПСО`, `ВерсияШаблона`).
- Версии фиксируются (pin) и не обновляются «вслепую» — каждая замена пакета
  проверяется на совместимость с интерпретатором pyRevit.
- Команда, зависящая от вендора, должна делать **самопроверку импорта** на старте
  и понятно сообщать пользователю, если зависимость недоступна, а не падать с
  «голым» `ImportError`.

## 5. Взаимодействие с GSD

- GSD (`.github/get-shit-done/`, `.planning/`) используется для планирования
  фаз, маппинга кодовой базы и валидации, **а не** для рантайма плагинов.
- Артефакты планирования живут в `.planning/codebase/*` (STRUCTURE, ARCHITECTURE,
  CONVENTIONS, CONCERNS, STACK, INTEGRATIONS, TESTING) и являются источником
  истины по конвенциям — при изменении правил разработки синхронизировать их.
- Внешние интеграции (Brave Search, Firecrawl) применяются только в GSD-
  автоматизации и не входят в рантайм кнопок.
- CLI: `node .github/get-shit-done/bin/gsd-tools.cjs <команда>` управляет
  состоянием `.planning/`.

## 6. Сохранение сессий и база знаний

Хранилище знаний — `MMLabs_OBSIDIAN/`. По команде пользователя
**«сохрани сессию»** выполняется обязательный ритуал:

1. Создать заметку в `MMLabs_OBSIDIAN/sessions/` с датой и сводкой.
2. Обновить `00-home/текущие приоритеты.md`.
3. Решение → заметка в `knowledge/decisions/`; баг → `knowledge/debugging/`.
4. Обновить `00-home/index.md` при появлении новых заметок.
5. Сделать **отдельный git commit** только по файлам текущей сессии в формате:
   `session: YYYY-MM-DD summary`.

> Требование отдельного коммита по сессии зафиксировано как обязательное
> (см. `sessions/2026-06-10 ...`). При старте сессии читать `00-home/index.md`
> и `текущие приоритеты.md`.

## 7. Поддержка и контроль качества

### 7.1. Ручная проверка (минимум перед выпуском)

- Кнопка появляется на ленте в нужной панели и в нужном порядке.
- Заголовок/тултип корректны на `ru` (и `en_us`).
- Команда отрабатывает на тестовой модели; ошибки показываются в UI, а не
  «молча» проглатываются.
- Транзакции корректно откатываются при сбое.

### 7.2. Известные риски качества (из `.planning/codebase/CONCERNS.md`)

- **Тихие `except`** скрывают критические ошибки (`Замена CAD-геометрии`,
  `ВерсияШаблона`, `Сброс потерь`, `Приточный по классификации`).
- **Дублирование** ~120 строк между ИОС-скриптами (`Сброс потерь`,
  `Приточный по классификации`, `Конфузор-Диффузор`, `Доп расход 0/1`).
- **Деструктив без подтверждения**: массовые `doc.Delete(...)` в
  `Замена CAD-геометрии`, часть внутренних ошибок проглатывается.
- **Производительность**: полные сканы модели и квадратичные проверки bbox.
- **Дрейф вендора** `lib/openpyxl` и отсутствие самопроверки импорта.
- **Нет централизованного логирования** сбоев мутаций и **нет автотестов**.

### 7.3. Приоритеты поддержки

1. Убрать silent-fail поведение.
2. Снизить стоимость изменений (тонкие кнопки, вынос общей логики в модули).
3. Добавить базовую защиту от регрессий.

## 8. Чек-лист перед мёрджем (Pull Request)

- [ ] `script.py` начинается с `# -*- coding: utf-8 -*-` и имеет
      `__title__`/`__author__`/`__doc__`.
- [ ] Нет «тихих» `except`; запись в модель обёрнута в транзакцию с откатом.
- [ ] Общая логика не скопирована между кнопками.
- [ ] Деструктивные операции имеют preflight-сводку и подтверждение.
- [ ] Нет повторных полных сканов модели/квадратичных проверок на больших данных.
- [ ] Вендорные зависимости запинены, есть самопроверка импорта.
- [ ] Кнопка добавлена в `layout` родительской панели.
- [ ] `bundle.yaml` кнопки и панели заполнены и локализованы.
- [ ] В индекс не попали `.vs/`, `__pycache__/`, временные отчёты.
- [ ] Изменения конвенций отражены в `.planning/codebase/*`.
- [ ] Коммит-сообщение содержательное; ветка — feature-ветка.
