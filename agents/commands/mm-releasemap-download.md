# /mm-releasemap-download — скачать Карту релизов в planning-документы

Ресинк плановых документов GSD из CSV-экспорта Google-таблицы «Сводный Реестр
Плагинов», лист **«Скрипты_Карта релизов»**. «Скачать» = взять свежий экспорт
листа и перегенерировать из него `.planning/*`. За один проход, без уточняющих
вопросов (Регламент, п. 8.2.1 и 11.3).

Инструмент — `RELEASE_MAP/gsd_release_sync.py` (только stdlib, без Revit).
Источник правды — CSV; плановые документы из него выводятся детерминированно.

## Предпосылка

Перед запуском пользователь выгружает свежий экспорт листа в
`RELEASE_MAP/Сводный Реестр Плагинов - Скрипты_Карта релизов.csv`.
Если экспорт не обновляли — предупреди, что синк пройдёт по текущему CSV,
и продолжай.

## Аргументы

Аргументов нет. Всё, что передал пользователь, трактуй как уточнение вывода
(например, «покажи только пропуски») — саму процедуру это не меняет.

## Правила синхронизации

Лист устроен так: строка-заголовок релиза (заполнена только «Версия релиза»,
формат `vYYMMDD`) задаёт релиз для всех идущих ниже строк-заданий.

- задание со статусом **«Без статуса»** (или пустым) **не синхронизируется**;
- задание с пустым **«Название плагина»** **не синхронизируется**;
- **MVP = TRUE** → приоритет `MVP`, иначе `Обычный`;
- жизненный цикл статусов: `Не начато → В работе → Готово → Релиз`.

Пропущенные задания остаются в CSV, перечисляются в отчёте и в секции
«Не синхронизировано» в `ROADMAP.md` — это сигнал дозаполнить строку в
Google-таблице, а не потеря данных.

## Процедура

1. `python3 RELEASE_MAP/gsd_release_sync.py check` — валидация структуры листа
   (обязательные колонки, формат версии релиза, дубли ID, допустимые статусы,
   задания до первого заголовка релиза). Exit-код `1` = невалидно: перескажи
   ошибки по-русски, укажи номера строк листа и **остановись** — правки вносит
   пользователь в Google-таблице, затем повторная выгрузка CSV.
2. `python3 RELEASE_MAP/gsd_release_sync.py sync-docs` — перегенерировать
   `.planning/release-map.json`, `.planning/ROADMAP.md`,
   `.planning/REQUIREMENTS.md`, `.planning/PROJECT.md` и копию
   `RELEASE_MAP/output/release-map.json` для выгрузки на сетевой диск.
   Эквивалент шагов 1–2 одной командой: `... sync`.
3. Проверь блок «ПРОПУСК» в выводе: перечисли пользователю задания, которые не
   попали в план, с причиной и номером строки листа.
4. Проверь блок «ПРОГРЕСС СОХРАНЁН» (если есть): скрипт оставил более
   продвинутый статус из прошлого `release-map.json` и зафиксировал его обратно
   в CSV — сообщи об этом, такие строки нужно поправить в Google-таблице.
5. При необходимости обнови `.planning/STATE.md` вручную: скрипт его не трогает
   (это файл состояния GSD — текущая фаза, прогресс, decisions log).
6. Покажи краткий итог (сколько заданий синхронизировано, сколько пропущено,
   какие файлы обновлены) и предложи коммит
   `docs: sync planning docs with release map`.

## Гейты и запреты

- **Не редактируй CSV вручную.** Смена статуса задания — только
  `python3 RELEASE_MAP/gsd_release_sync.py status <ID> "<статус>"` (она же пишет
  журнал переходов `RELEASE_MAP/status-journal.csv`). Правки состава заданий
  делает пользователь в Google-таблице и перевыгружает CSV.
- **Не редактируй текст между маркерами** `<!-- RELEASE-MAP:BEGIN -->` и
  `<!-- RELEASE-MAP:END -->` в `.planning/*.md` — он перезаписывается при каждом
  синке. Ручной текст **вне** маркеров (например, фазы GSD `## Phase N: ...`
  в `ROADMAP.md`) регенерацию переживает — не переноси его внутрь блока.
- При первой миграции файла без маркеров скрипт кладёт резервную копию в
  `.planning/_legacy/` (каталог в `.gitignore`) — упомяни её, если она появилась.
- Не запускай `sync-docs`, если `check` вернул ошибки: скрипт всё равно
  откажется работать (fail-fast), но пользователь должен увидеть причину.
- Не коммить без запроса пользователя (Git-регламент, D-18): предложи коммит
  и пофайловый `git add` затронутых путей.

## Финал

Сообщи пользователю:

- итог `check` (exit-код и трактовка);
- сколько заданий синхронизировано и сколько пропущено — с причинами;
- список обновлённых файлов;
- предложенный коммит и напоминание, что состав заданий правится в
  Google-таблице, а статусы — подкомандой `status`.
