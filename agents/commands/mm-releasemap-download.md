# /mm-releasemap-download — скачать Карту релизов в planning-документы

Ресинк плановых документов GSD из CSV-экспорта Google-таблицы «Сводный Реестр
Плагинов», лист **«Скрипты_Карта релизов»**. «Скачать» = взять свежий экспорт
листа и перегенерировать из него `.planning/*`. За один проход, без уточняющих
вопросов (Регламент, п. 8.2.1 и 11.3).

Инструмент — `RELEASE_MAP/gsd_release_sync.py` (только stdlib, без Revit).
Источник правды — CSV; плановые документы из него выводятся детерминированно.

## Предпосылка

Перед запуском пользователь выгружает свежий экспорт листа из Google-таблицы
в каталог «Загрузки» — `%USERPROFILE%\Downloads` (обычное скачивание браузером,
файл никуда перекладывать не нужно). Оттуда шаг `fetch` копирует его в
`RELEASE_MAP/Сводный Реестр Плагинов - Скрипты_Карта релизов.csv`; дальше вся
работа идёт с копией в репозитории.

`fetch` берёт файл с именем `Сводный Реестр Плагинов - Скрипты_Карта релизов.csv`,
включая варианты с браузерным суффиксом (`… (1).csv`) — из них самый свежий по
времени изменения. Файл в «Загрузках» не удаляется.

Если свежей выгрузки в «Загрузках» нет — `fetch` печатает `ВНИМАНИЕ` и оставляет
текущий CSV репозитория: предупреди пользователя, что синк пройдёт по нему,
и продолжай. Останов только если CSV нет и в «Загрузках», и в репозитории
(`fetch` завершится с кодом 1).

## Аргументы

Аргументов нет. Всё, что передал пользователь, трактуй как уточнение вывода
(например, «покажи только пропуски») — саму процедуру это не меняет.

## Соответствие с GSD

- версия релиза `vYYMMDD` → **фаза GSD** `Phase vYYMMDD`;
- ID задания → **требование GSD** `REQ-<ID>` (например `REQ-2830001`);
- **дата фазы — только из версии релиза** (`v260814` → `2026-08-14`). Колонка
  «План релиза» — рудимент листа, не импортируется; версия с несуществующей
  датой — ошибка `check`;
- **статус «Релиз» подтверждает закрытие требования в GSD** (`- [x]`). «Готово»
  закрытием не считается. Статус фазы выводится из её требований:
  `Не начата` → `В работе` → `Готова к релизу` (все `Готово`/`Релиз`) →
  `Закрыта релизом` (все `Релиз`). Переходы печатаются блоком `ЗАКРЫТО:`.

## Правила синхронизации

Лист устроен так: строка-заголовок релиза (заполнена только «Версия релиза»,
формат `vYYMMDD`) задаёт релиз для всех идущих ниже строк-заданий.

- задание со статусом **«Без статуса»** (или пустым) **не синхронизируется**;
- задание с пустым **«Название плагина»** **не синхронизируется**;
- **MVP = TRUE** → приоритет `MVP`, иначе `Обычный`;
- жизненный цикл статусов: `Не начато → В работе → Готово → Релиз`;
- **новое задание заводится в GSD только со статусом «Не начато»**. Задание,
  которого не было в прошлом `.planning/release-map.json` и которое приехало из
  листа сразу «В работе»/«Готово»/«Релиз», — работа мимо GSD: в план не попадает,
  уходит в пропуски с причиной «новое задание не в статусе «Не начато»».
  Исключение — самый первый синк (базы ещё нет): тогда заводится весь состав;
- **уже заведённые задания обновляются из CSV целиком** — статус (в том числе
  откат назад по циклу), описание, комментарий, даты, автор, вес, группа, MVP.
  Прошлый `release-map.json` значения не переопределяет и в CSV ничего не
  дописывает; задание, удалённое из листа, уходит из плановых документов.

Единственный источник значений — CSV «Карта релизов». Правки в `.planning/*`
руками бессмысленны: следующий синк их перезапишет.

Пропущенные задания остаются в CSV, перечисляются в отчёте и в секции
«Не синхронизировано» в `ROADMAP.md` — это сигнал дозаполнить строку в
Google-таблице, а не потеря данных.

## Смена набора заданий (`reset`)

Если пользователь загружает **принципиально новый набор заданий** (другой лист,
другая нумерация ID, новые релизы) — перед синком выполни
`python3 RELEASE_MAP/gsd_release_sync.py reset`. Он очищает генерируемые блоки
`.planning/ROADMAP.md`, `REQUIREMENTS.md`, `PROJECT.md` и обнуляет baseline
`.planning/release-map.json`.

Что `reset` НЕ трогает — ручной текст вне маркеров (фазы GSD `## Phase N: ...`),
`.planning/STATE.md`, `.planning/phases/`, `.planning/codebase/`, `quick/`.
Текущие фазы GSD переживают смену набора: пространства имён не пересекаются —
фаза Карты релизов это `Phase vYYMMDD`, фаза GSD — `Phase N: <название>`;
требование Карты релизов — `REQ-<ID>`, требования GSD — свои коды (`CONV-*`).

Baseline именно **обнуляется**, а не удаляется: пустая база означает «в GSD нет
ни одного требования», поэтому гейт «новое требование только со статусом
«Не начато»» работает уже на первом синке нового набора. При удалённом файле
включился бы режим первого запуска и в план заехал бы весь лист в любых статусах.

Закрывать milestone ради нового набора заданий НЕ нужно — это независимые вещи:
milestone относится к фазам GSD, а не к Карте релизов. Если milestone всё же
нужно закрыть, это делают команды GSD (`/gsd-complete-milestone` →
`/gsd-new-milestone`), а не этот скрипт.

## Процедура

1. `python3 RELEASE_MAP/gsd_release_sync.py fetch` — забрать свежий экспорт листа
   из `%USERPROFILE%\Downloads` в `RELEASE_MAP/`. Возможные исходы: `загружено:`
   (CSV обновлён), `совпадает с текущим CSV` (выгрузка та же — копирования нет),
   `ВНИМАНИЕ` (в «Загрузках» пусто — идём по текущему CSV, скажи об этом
   пользователю), exit-код `1` (CSV нет нигде — **остановись**, попроси выгрузить
   лист из Google-таблицы).
2. `python3 RELEASE_MAP/gsd_release_sync.py check` — валидация структуры листа
   (обязательные колонки, формат версии релиза, дубли ID, допустимые статусы,
   задания до первого заголовка релиза). Exit-код `1` = невалидно: перескажи
   ошибки по-русски, укажи номера строк листа и **остановись** — правки вносит
   пользователь в Google-таблице, затем повторная выгрузка CSV. `check` проверяет
   только структуру листа, поэтому его «синхронизируется N» может быть больше,
   чем итог `sync-docs`: гейт новых заданий применяется на шаге 3.
3. `python3 RELEASE_MAP/gsd_release_sync.py sync-docs` — перегенерировать
   `.planning/release-map.json`, `.planning/ROADMAP.md`,
   `.planning/REQUIREMENTS.md`, `.planning/PROJECT.md` и копию
   `RELEASE_MAP/output/release-map.json` для выгрузки на сетевой диск.
   Эквивалент шагов 1–3 одной командой: `... sync`.
4. Проверь блок «ПРОПУСК» в выводе: перечисли пользователю задания, которые не
   попали в план, с причиной и номером строки листа. Причина «новое задание не в
   статусе «Не начато»» — не ошибка формата: так гейт отсекает работу, сделанную
   мимо GSD; чтобы завести такое задание, статус в Google-таблице надо выставить
   в «Не начато».
5. Проверь блоки «ОБНОВЛЕНО» и «ЗАКРЫТО»: первый — что приехало из нового CSV
   (новые требования, изменённые поля, выпавшие и удалённые), второй — какие
   требования новый CSV закрыл статусом «Релиз» и какие фазы от этого закрылись.
   Перескажи оба: это и есть ответ на вопрос «что изменилось».
6. При необходимости обнови `.planning/STATE.md` вручную: скрипт его не трогает
   (это файл состояния GSD — текущая фаза, прогресс, decisions log).
7. Покажи краткий итог (сколько заданий синхронизировано, сколько пропущено,
   какие файлы обновлены) и предложи коммит
   `docs: sync planning docs with release map`.

## Гейты и запреты

- **Не перекладывай CSV руками.** Копирование из «Загрузок» в `RELEASE_MAP/` —
  только шагом `fetch`: он же выбирает самую свежую выгрузку и не трогает
  оригинал в «Загрузках». Файлы пользователя в «Загрузках» не удаляй.
- **Не редактируй CSV вручную.** Параметры заданий (статус, описание,
  комментарий, даты, MVP, вес, группа) меняются исключительно в Карте релизов —
  пользователь правит Google-таблицу и перевыгружает CSV. Локальная смена
  статуса — только `python3 RELEASE_MAP/gsd_release_sync.py status <ID> "<статус>"`
  (она же пишет журнал переходов `RELEASE_MAP/status-journal.csv`); предупреди,
  что правка живёт до следующего `fetch` и её всё равно надо перенести
  в Google-таблицу.
- **Не подставляй значения за CSV.** `sync-docs` не переносит статусы из прошлых
  прогонов и не дописывает их обратно в CSV: расхождение — сигнал поправить лист,
  а не повод «сохранить прогресс».
- **Не редактируй текст между маркерами** `<!-- RELEASE-MAP:BEGIN -->` и
  `<!-- RELEASE-MAP:END -->` в `.planning/*.md` — он перезаписывается при каждом
  синке. Ручной текст **вне** маркеров (например, фазы GSD `## Phase N: ...`
  в `ROADMAP.md`) регенерацию переживает — не переноси его внутрь блока.
- При первой миграции файла без маркеров скрипт кладёт резервную копию в
  `.planning/_legacy/` (каталог в `.gitignore`) — упомяни её, если она появилась.
- Не запускай `sync-docs`, если `check` вернул ошибки: скрипт всё равно
  откажется работать (fail-fast), но пользователь должен увидеть причину.
- Не коммить без запроса пользователя (Git-регламент, D-18): предложи коммит
  и пофайловый `git add` затронутых путей.

## Финал

Сообщи пользователю:

- итог `fetch`: какой файл из «Загрузок» взят (или что взят текущий CSV репозитория);
- итог `check` (exit-код и трактовка);
- сколько заданий синхронизировано и сколько пропущено — с причинами;
- список обновлённых файлов;
- предложенный коммит и напоминание, что состав заданий правится в
  Google-таблице, а статусы — подкомандой `status`.
